# Contributing to pdf

Thank you for your interest in contributing to `pdf`! This document describes how to set up the project, which checks a change must pass, and how releases are made.

## Development Setup

### Prerequisites

- Node.js `^20.19.0 || >=22.12.0` (CI uses Node.js 24)
- npm (the repository is an npm workspace locked with `package-lock.json`)
- The rendering specs use `canvas`, which needs its native dependencies (Cairo, Pango) on some platforms; see the [node-canvas install notes](https://github.com/Automattic/node-canvas#compiling)

### Installation

```bash
git clone https://github.com/PeculiarVentures/pdf.git
cd pdf
npm ci
npm test
npm run build
```

## Project Layout

- `packages/<name>/` is the `@peculiar/pdf-<name>` package: `core` (PDF objects, parsing, writing, encryption), `doc` (documents, pages, forms, signatures), `font`, `copy`, `form-json`, `repair` and `cli` (the `pvpdf` command).
- `packages/tests/` (`@peculiar/pdf-tests`) is a private package with test helpers and resources (PKI helpers, page rendering through pdfjs-dist). It is never built or published.
- `packages/<name>/src/index.ts` is the package's only public entry point and must stay aligned with its `exports`.
- `tsdown.config.ts` at the repository root builds every package (tsdown `workspace` mode). There are no per-package build configs.
- `tsconfig.json` at the root is used for typechecking, tests and the declaration build. Its `paths` map every `@peculiar/pdf-*` package to its `src`, so packages and tests use the sibling sources without building them first.
- `packages/<name>/build/` is generated by `npm run build` and is not committed.
- `packages/font/scripts/default.ts` regenerates `packages/font/src/DefaultFonts.ts` from `packages/font/fonts/` (`npm run build`, then `npm run scripts:default --workspace packages/font`).

## Development Workflow

### Code Quality

Before opening a pull request, run from the repository root:

```bash
npm run lint          # oxlint
npm run format:check  # oxfmt
npm run typecheck     # tsc --noEmit
npm test              # vitest, runs once and exits
npm run build         # tsdown, also checks every package with attw
```

Fix lint and formatting issues with `npm run lint:fix` and `npm run format`. Use `npm run coverage` to produce a coverage report, and `npx vitest run packages/<name>` to run one package's tests. Run `npm test` after `npm run build` to also run `packages/tests/src/build.spec.ts`, which loads every built package in a fresh Node.js process.

### Testing

- Use Vitest: import `describe`, `it` and `expect` from `vitest` (globals are off) and assert with `expect`.
- Put tests next to the code they cover as `*.spec.ts`.
- Cover new behavior and bug fixes with tests. For parsing or writing changes, check the exact bytes or a round trip.
- `vitest.config.ts` loads `reflect-metadata`, which `@peculiar/x509` needs.
- Some signing specs request timestamps from a public TSA, and the rendering specs compare page image hashes per platform (`darwin`, `linux`). Update both hashes when a change affects rendering.

### Build And Package Exports

Every package is ESM-only; there is no CommonJS build, and CommonJS consumers load it through `require(esm)`. tsdown bundles each package's `src/index.ts` into `build/index.js` with `build/index.d.ts` (`unbundle: false`: core and doc have import cycles that decorators and module-level registrations only survive in bundled order). The syntax target comes from `engines.node`; do not set `target` in `tsdown.config.ts`.

`exports` and the legacy `main`/`module`/`types` fields in each `packages/<name>/package.json` are generated by tsdown on every build and must not be edited by hand. CI fails if the build changes a `package.json`. pdf-cli's `bin` is written by hand (`exports.bin` is off); its `src/index.ts` starts with the shebang, which the build keeps.

Use named exports only (no `export default`) and no top-level `await`, so `require()` of the packages keeps working on supported Node.js versions. Use `import type` for type-only imports (`verbatimModuleSyntax`).

`sideEffects` is `true` for core, doc and repair: they register PDF object types, form components, CMS algorithms and attributes, and repair rules when their modules load (some through imports such as `import "./register"`), and tsdown applies the package's own `sideEffects` field to its sources, so `false` would drop those registrations from the build. font, copy and form-json have `"sideEffects": false`.

### Dependencies

- `@peculiar/x509` and `pkijs` are **peer** dependencies (and dev dependencies) of core and doc, `asn1js` of doc, and `@peculiar/asn1-schema` of doc and font: pdf takes and returns their objects, checks them with `instanceof`, and uses the pkijs engine and x509 crypto provider the application sets, so an app must have only one copy.
- The `@peculiar/asn1-*` schema packages, `@peculiar/utils`, `bytestreamjs`, `pako`, `fast-png`, `fontjs` and `events` are regular `dependencies`. Use the `@peculiar/utils` root or subpath entries, never `/legacy`.
- Pass values that go to WebCrypto, pkijs or x509 as ArrayBuffer-backed data (`toArrayBuffer`, or `toCryptoBytes` in core's encryption code); pdf's own signatures take `@peculiar/utils`' `BufferSource`.
- pdf-cli is an application: everything it needs, including the libraries' peers, is in its `dependencies`, and it loads `reflect-metadata` itself.
- Internal `@peculiar/pdf-*` ranges are bumped by the release pull request; don't change them by hand.

### Commit Messages

Use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). Pull requests are squash-merged, so the pull request title becomes the commit message and must follow the same format.

```plain
type(scope): description

[optional body]

[optional footer]
```

Types: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`, `style`, `revert`. Use the package directory as the scope for package-specific changes (for example `fix(core): ...`, `feat(doc): ...`).

Mark breaking changes with `!` after the type or scope (for example `feat(doc)!: ...`) and/or a `BREAKING CHANGE:` footer.

### Pull Requests

1. Fork the repository and create a branch from `main`.
2. Make your changes, with tests.
3. Run the checks listed above.
4. Open a pull request with a Conventional Commit title.

## Code Style

- Write TypeScript.
- Follow the oxlint (`.oxlintrc.json`) and oxfmt (`.oxfmtrc.json`) configuration.
- Keep changes small and localized to the owning package.
- Prefer `BufferSource`-based public APIs over Node.js-specific `Buffer` types; the libraries also run in browsers.
- Keep public exports stable; breaking changes need a major release.

## Releases

Releases are managed by [release-please](https://github.com/googleapis/release-please) (`release-please-config.json`, `.release-please-manifest.json`). All packages share one version and are released together.

1. On every push to `main`, the **Release** workflow first runs lint, format, typecheck, tests, and build (the **Test** workflow). Only when they pass does release-please open or update a `chore(release): vX.Y.Z` pull request. It bumps the root and every `packages/*/package.json` version, the internal `@peculiar/pdf-*` ranges, and `package-lock.json`. The version comes from the commits: a breaking change bumps major, `feat` bumps minor, and `fix`, `perf`, `build`, and `revert` bump patch. Other types do not trigger a release. Any releasable commit releases every package, including commits that only touch root files.
2. Merge the release pull request. release-please creates one `vX.Y.Z` tag and one GitHub Release with the notes from the pull request; the workflow then publishes every public package whose version is not on npm yet via Trusted Publisher, with provenance, dependencies first, and moves the major tag (for example `v2`) when this is the newest release of that major.

To retry a failed or partial npm publish, run **Release** manually from the `vX.Y.Z` tag; packages already on npm are skipped. Set the optional `RELEASE_TOKEN` secret (PAT or GitHub App token) so the Test workflow runs on the release pull request. Every published package needs an npm Trusted Publisher for this repository, workflow `release.yml` and environment `npm`.

Release notes live only in [GitHub Releases](https://github.com/PeculiarVentures/pdf/releases); there is no `CHANGELOG.md`. Only `feat`, `fix`, `perf`, `build`, `revert`, and breaking changes are listed. Force a version with a `Release-As: x.y.z` line in a commit body. To fix the notes for a merged change, add a `BEGIN_COMMIT_OVERRIDE` … `END_COMMIT_OVERRIDE` block with the corrected commit message to that pull request's description; edits to the release pull request description are overwritten when new commits land.
